How Recommendation Agent works

You give it a task name. It pulls that task's real run history from Athena, runs it through an LLM agent built on definity's own tuning knowledge, and hands back Spark config changes with the reasoning and the dollar impact behind each one — not a suggestion pulled from memory, but one grounded in this specific run's telemetry.

The pipeline

Every analysis runs the same nine steps, in order:

  • Fetch context→
  • Entry gate→
  • SQL rules→
  • Agent discovery→
  • Merge insights→
  • Triage→
  • Plan→
  • Safety check→
  • Explain
Fetch context

Pulls the task's latest completed run, its config history, and up to 20 prior runs from Athena.

Entry gate

Refuses to analyze anything but a COMPLETED run — no guessing from a run still in progress.

SQL rules

Deterministic checks (idle time, GC pressure, retries, over-provisioning, …) that definity already runs in production, replayed here.

Agent discovery

The LLM inspects telemetry the SQL rules don't cover, using definity's own knowledge base — physics of Spark memory/compute/shuffle, known failure playbooks — as its reference.

Merge insights

Combines the SQL-rule and agent-discovered findings into one list, deduplicated.

Triage

Ranks findings into health-first tiers and resolves ones that conflict (e.g. two changes to the same executor-memory setting).

Plan

Turns each surviving finding into a concrete config change, with a dollar-cost estimate priced from this task's own historical run cost — never a guessed percentage.

Safety check

Blocks or defers anything that violates a hard rule — a cost increase with no measured problem to justify it, two changes to the same coupled setting, a config key that doesn't exist for this Spark version.

Explain

Writes the plain-language why/how/risk for every change that survives, which is what you see on the results screen.

What grounds it

The reasoning isn't free-form. Every step above draws on a written knowledge base of Spark internals (how memory, shuffle, driver sizing and cluster autoscaling actually behave) plus a set of hard safety rules the plan can never override — so a change has to earn its place with real evidence and can't contradict itself with another change in the same plan.

Data & limits

Task data comes from an Athena export of definity's production tables, which lags live production — the freshest run visible here may be a few hours or a day old (see the "Athena export" indicator above). Every job's dump, working files and results are deleted a few hours after it finishes; download the JSON if you need to keep it.
